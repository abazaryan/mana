# Модель данных «Маны» (IndexedDB)

Этап 4.1, дополнено на этапах 4.2, 4.3, 5, 6а.3 (синхронизация, Р39) и 6а.4 (перенос ответов в аккаунт, Р40). Основано на решениях Р2, Р3, Р4, Р8, Р10, Р15, Р17, Р18, Р22, Р25, Р26 (`docs/DECISIONS.md`). Схема подтверждена владельцем продукта 11.10.2026 с поправками (Р18). Хранилище — IndexedDB через Dexie, база `mana`, версия схемы 2 (этапы 4.2 и 4.3 добавили только необязательные поля журнала и тип записи `drill` — индексы не менялись; **версия 2 — этап 6а.3: только новая таблица `outbox`**, данные не переносятся и не меняются; первое обновление схемы на телефоне, см. «Очередь отправки»). Код: типы — `src/core/model.ts`, схема — `src/platform/db.ts`, чтение и запись — `src/platform/repo.ts`. Прототип (`localStorage`, ключи `sluh.settings` и `sluh.log`) остаётся как есть и в новую базу не переносится.

## Коротко

Данные делятся на три вида:

| Вид | Что это | Откуда берётся | Что с ним при синхронизации (этап 6) |
|---|---|---|---|
| **Содержимое колод** | колоды, записи, аудио | из ZIP-файла при импорте | одинаково на всех устройствах (по `id` колоды и записей); позже — из общей библиотеки |
| **Журнал** | что и когда пользователь делал: знакомства и ответы | пишется при занятиях, **только дополняется** | журналы устройств объединяются (по UUID записей журнала) |
| **Производное** | состояние FSRS каждой карточки | вычисляется из журнала | не передаётся: после объединения журналов пересчитывается |

Плюс две маленькие таблицы: настройки пользователя и служебные сведения устройства (локальный `userId`, `deviceId`).

Главное правило: **источник правды о прогрессе — журнал.** Состояние FSRS хранится в базе только чтобы быстро собирать сессию; его можно стереть и пересчитать из журнала, ничего не потеряв (Р10).

## Ключи и идентификаторы

- **Колода** — `deckId` из `deck.json` (устойчивый, задаёт автор колоды).
- **Запись колоды** — пара `deckId` + `entryId` (оба из `deck.json`). Случайный UUID записям колоды **не нужен**: одна и та же колода, импортированная на телефоне и на ноутбуке, должна получить одинаковые ключи, иначе прогресс не сведётся. Устойчивые `id` уже дают это (Р2).
- **Карточка** — запись × навык: `deckId` + `entryId` + `skill` (`listen` / `speak` / `write`, Р3).
- **Запись журнала** — UUID v4 (`crypto.randomUUID()`), создаётся на устройстве. По нему журналы объединяются без конфликтов.
- **Пользователь** — локальный `userId` (UUID), создаётся при первом запуске. При входе с переносом ответов (6а.4, Р40) первая установка отдаёт аккаунту свой `userId` (записи не переписываются); следующая установка со своими ответами один раз, до первой отправки, меняет `userId` своих записей на id аккаунта, а её прежний `userId` сервер запоминает как прежний номер установки аккаунта (`user_aliases`).
- **Устройство** — `deviceId` (UUID), тоже при первом запуске. Нужен, чтобы при синхронизации и разборе журнала видеть, с какого устройства ответ.
- Время — абсолютные моменты (`Date`, хранится как есть). С этапа 4.4а (Р29.3) каждая запись журнала хранит и пояс устройства в тот момент (`tz`, `tzOffsetMin`): по нему считаются сутки приложения записи (граница 04:00 местного). Записи без пояса (до 4.4а) считаются Europe/Luxembourg. «Сегодня» (лимит, добор, долги, числа в конце порции) считается по поясу устройства в момент подсчёта. Модуль — `src/core/zone.ts`.

### `entries` — записи колод

Ключ `[deckId+entryId]`. Индексы: `deckId`, `[deckId+position]`.

| Поле | Тип | Что это |
|---|---|---|
| `deckId`, `entryId` | string | |
| `position` | number | порядок в колоде = порядок знакомства (Р15) |
| `hidden` | `0 \| 1` | 1 — записи нет в установленной редакции (Р15); такая запись не выдаётся (Р17.9), но её прогресс и журнал сохраняются |
| `text`, `ipa`, `meaning`, `hint`, `note`, `speech`, `gender`, `form`, `tags`, `skills` | как в `deck.json` | см. `docs/DECK_FORMAT.md`; `speech` (Р34) — необязательное поле без индекса, новая версия базы не нужна |
| `audio` | string \| null | путь внутри архива (`audio/le-nom.mp3`) — ключ в таблице `media` |

`hidden` хранится числом, а не `true/false`: IndexedDB не умеет индексировать логические значения.

### `media` — аудио колод

Ключ `[deckId+path]`. Индекс `deckId`. Отдельно от `entries`, чтобы список записей грузился без мегабайтов звука.

| Поле | Тип | Что это |
|---|---|---|
| `deckId` | string | |
| `path` | string | `audio/le-nom.mp3` |
| `type` | string | `audio/mpeg` или `audio/wav` |
| `data` | ArrayBuffer | сам файл |
| `bytes` | number | размер |

Звук хранится как `ArrayBuffer`, а не `Blob`: так надёжнее во всех браузерах; для воспроизведения из него создаётся `Blob` и временная ссылка.

### `log` — журнал (только дополняется)

Ключ `id` (UUID). Индексы: `[userId+at]` (ответы за сегодня, лимит новых), `[userId+deckId+entryId+skill+at]` (история карточки: пересчёт FSRS, «предыдущий ответ» для «Легко», Р4), `[userId+deckId+entryId+type]` (было ли знакомство).

Записи никогда не меняются и не удаляются. Если когда-нибудь понадобится отменить ответ, это будет новая запись журнала, которая ссылается на отменяемую. **Одно исключение (6а.4, Р40 п. 7):** при переносе ответов в аккаунт у записей прежнего номера установки один раз, до их первой отправки, меняется `userId` на id аккаунта; остальные поля — те же.

Общие поля всех записей:

| Поле | Тип | Что это |
|---|---|---|
| `id` | string (UUID) | |
| `type` | `'intro' \| 'review' \| 'drill'` | знакомство, ответ или короткое повторение после «Снова» (с этапа 4.3; новые типы добавляются без смены схемы) |
| `userId`, `deviceId` | string | |
| `at` | Date | момент события |
| `deckId`, `entryId` | string | |
| `deckRevision` | number | редакция колоды в момент события |

| `tz` | string? | пояс устройства (IANA, например `Europe/Luxembourg`; `local`, если браузер его не назвал) — с 4.4а (Р29.3) |

**Знакомство** (`type: 'intro'`, Р3) — одно на запись, без оценки. Дополнительно: `skill: null`; с этапа 4.2 (Р22.5) — необязательные `echo` («повторите вслух»: `answer`, `alternatives`, `verdict` или `null`, `skipped`) и `copy` («напишите по образцу», только у записей с `write`: `typed`, `verdict`, `errorType`). С 16.10.2026 в `echo` также `repeatHintShown` (Р23), `mode` (`voice` / `typed` — после трёх нераспознанных попыток), `recognitionErrors`, `retries`, `repeats`. Запись пишется, когда пользователь нажал «Дальше» на карточке знакомства; ушёл с середины — знакомства нет. После него навыки записи можно выдавать как новые карточки (строка в `cards` появится с первым ответом). Знакомства за сегодня считаются в лимит новых (Р17.5), в том числе со скрытыми записями (Р17.9).

| `speechPack` | `'available' \| 'downloadable' \| 'downloading' \| 'unavailable' \| 'unsupported'` \| null | состояние языкового пакета на устройстве в начале порции (только при включённых подсказках) — с 15.10.2026 |
| `suggested` | 1–4 | предложенная оценка (Р4) |
| `reason` | `RatingReason` | почему предложена (`incorrect`, `almost`, `correct`, `correct-fast`, `correct-fast-twice`, `correct-retried` — «Легко» не предложено из-за повторов или нераспознанных попыток в этой карточке; `listen-no-easy` — в `listen` «Легко» автоматически не ставится, Р25) |
| `punctuationNote` | boolean | `write`: ответ отличается от эталона только пунктуацией в каких-то местах — она показана нейтрально и не учитывается (Р26); с 17.10.2026. То же поле — в `copy` знакомства и короткого повторения |
| `keyboard` | `'onscreen' \| 'system' \| 'physical'` \| null | ответ текстом: чем набран первый символ — своей клавиатурой, клавиатурой устройства (настройка «Системная клавиатура») или физической; `null` — ничего не набрано, только вставлено (Р31, с этапа 5). То же поле — в `copy` и в `echo` (набор после трёх неудач) знакомства и короткого повторения |

| `plays` | number \| null | `listen`: сколько раз прозвучало аудио до ответа (1 — только автоматически; плюс нажатия «Такрор») — с 4.3 |
| `audioEndMs` | number \| null | `listen`: когда кончилось последнее прослушивание (видимые мс от показа карточки) — с 4.3 |

| `requeue` | number | 0 — карточка по плану порции; 1 или 2 — вернулась после «Снова» (Р25) — с 4.3. С 4.4а (Р29.2) возврат FSRS не меняет: снимок `fsrs` показывает состояние без изменений, пересчёт пропускает такие ответы в записях любой версии, «Легко» при поиске предыдущего ответа тоже их пропускает (`sincePairSec` — нет) |
| `sincePairSec` | number \| null | секунды с прошлого ответа по этой паре (запись × навык), в любой день; `null` — ответа не было — с 4.3 |
| `sinceEntryCards` | number \| null | сколько других карточек прошло с прошлой карточки той же записи в этой порции (знакомство считается); `null` — её не было — с 4.3 |
| `sinceEntrySec` | number \| null | секунды с конца прошлой карточки той же записи в этой порции; `null` — её не было — с 4.3 |
| `final` | 1–4 | окончательная оценка — **она идёт в FSRS** |
| `correction` | `null \| 'lowered' \| 'raised' \| 'misrecognized'` | правка пользователя (Р4); `misrecognized` — «Меня неправильно распознали» |
| `rules` | number? | версия правил расписания (`RULES_VERSION`; 2 — этап 4.4а: без шагов в минутах, сутки по поясу записи). Пересчёт применяет к записи правила её версии; записи без версии — по правилам 4.4а (Р29.4) |
| `fsrs` | снимок | состояние карточки до ответа и новый срок (как `ReviewSnapshot` в `scheduler.ts`) — **только для анализа**; при расхождении прав пересчёт из журнала |

Запись пишется один раз — когда пользователь нажал «Дальше» с окончательной оценкой. В `write` латентность — до первой клавиши, `totalMs` — до «Проверить» (Р21); в `listen` — от готовности микрофона после последнего прослушивания (при ответе текстом — от конца звука до первой клавиши).

**Короткое повторение** (`type: 'drill'`, Р17.11, Р25) — после ответа с окончательной оценкой «Снова»; пишется после записи ответа. Поля: `skill`, `reviewId` (id ответа), `skipped`, `echo` («повторите вслух» для `speak` и `listen`, та же форма, что у знакомства) или `copy` («напишите по образцу» для `write`). Без оценки: пересчёт FSRS (`rebuildCards` берёт только `review`) и поиск предыдущего ответа для «Легко» (`lastReview`) её пропускают — тест проверяет, что пересчёт с ней и без неё даёт те же `nextDue`. Резервная копия принимает этот тип.

**Поля этапа 4.4а.** `tz`, `tzOffsetMin` у всех записей, `rules` у ответа, `rulesVersion` в `meta`, `lastReviewOffsetMin` в `cards` — необязательные; индексы не менялись, версия схемы остаётся 1. Вместо миграции схемы — разовый пересчёт карточек (Р29.7). Формат файла журнала не меняется: восстановление пропускает новые поля как есть.

**Поля этапа 4.3.** Новые поля ответа необязательные, тип `drill` — новый тип записи; индексы не менялись, версия схемы остаётся 1, миграции нет.

**Поля этапа 4.2 и миграция.** Все новые поля необязательные: в старых записях их нет, и это корректно. Dexie хранит любые поля без объявления; меняются только индексы — их этап 4.2 не трогал, поэтому версия схемы остаётся 1 и миграции нет. Формат файла журнала (`mana-journal`, версия 1) тоже не меняется: восстановление проверяет обязательные поля и пропускает остальные как есть.

### `cards` — состояние FSRS (производное)

Ключ `[userId+deckId+entryId+skill]`. Индексы: `[userId+due]` (что пора повторять), `[userId+deckId]`.

| Поле | Тип | Что это |
|---|---|---|
| `userId`, `deckId`, `entryId`, `skill` | | |
| `due`, `stability`, `difficulty`, `elapsedDays`, `scheduledDays`, `reps`, `lapses`, `learningSteps`, `state`, `lastReview` | как `CardState` в `scheduler.ts` | `due` — реальный момент: время ответа + интервал |
| `lastReviewOffsetMin` | number \| null | смещение пояса последнего ответа (с 4.4а). **День срока** = сутки приложения последнего ответа + `scheduledDays`; карточка выдаётся, когда этот день наступил, и считается долгом, когда он прошёл (Р29.3, Р29.5) |
| `lastLogId` | string | последний учтённый ответ журнала |

Строка появляется с **первым ответом** по карточке. До него карточка «новая» (пустое состояние FSRS), строка для неё не нужна: что запись уже прошла знакомство, видно по журналу. Так таблица — в точности функция журнала. Каждый ответ в одной транзакции дописывает журнал и обновляет карточку. Функция `rebuildCards` (`src/core/cards.ts`) проигрывает журнал по порядку (`at`, затем `id`) через `ts-fsrs` с окончательными оценками и получает то же состояние.

**Детерминизм пересчёта (Р18).** Проверено по исходнику ts-fsrs 5.4.1:
- «fuzz» (случайный разброс сроков) у нас выключен (`enable_fuzz: false`);
- даже включённый, он не случаен: генератор ts-fsrs получает зерно из времени ответа, номера повторения и произведения сложности на стабильность, поэтому повторный расчёт даёт те же даты;
- дни ts-fsrs считает по UTC-датам; с этапа 4.4а переходник в `scheduler.ts` сдвигает каждый момент на (смещение пояса записи − 4 ч), поэтому ts-fsrs видит сутки приложения в поясе каждого ответа, а пояс устройства, которое пересчитывает, на результат не влияет.

Выбор: пересчёт из журнала — основной путь; дополнительно каждая запись ответа хранит рассчитанные тогда новое состояние и дату следующего повторения (`fsrs.nextState`, `fsrs.nextDue`). Это страховка на случай смены версии ts-fsrs или её параметров: по журналу всегда видно, какой срок был назначен. Тесты: пересчёт из журнала даёт те же карточки, что пошаговая запись, и ту же дату `nextDue` после каждого ответа, в том числе с включённым «fuzz». С этапа 4.4а правила сменились (Р29): сроки в записях без `rules` — история (что было назначено тогда); пересчёт применяет к ним правила 4.4а.

Если навык убран из записи в новой редакции, его карточка остаётся в базе, но не выдаётся; вернётся навык — вернётся и прогресс.

## Импорт колоды

Одна функция в `src/core/` решает, *что* изменить (чистая логика, тесты без браузера); запись в базу — в `src/platform/`, **одной транзакцией**: если что-то сломалось, остаётся прежняя редакция целиком.

1. Прочитать ZIP (JSZip) или `deck.json`, проверить тем же валидатором, что `npm run deck:check`. Есть ошибки — показать их и ничего не менять. Иначе — всегда окно «Натиҷаи санҷиш» (предупреждения, сведения, вопросы п. 4, что изменится), запись — только кнопкой (Р34).
2. Название — имя файла без `.zip` (`deckNameFromFileName`).
3. Колоды с таким `id` нет — установить.
4. Колода есть:
   - новая редакция **больше** установленной — обновить без вопросов;
   - **равна** — спросить «Редакция N уже установлена. Переустановить? Прогресс и журнал не изменятся.» (Р18);
   - **меньше** — предупредить «Загружается редакция N, а установлена M — загружаемая старее. Всё равно установить?» (Р15);
   - **записи почти не совпадают** (общих `id` меньше половины от меньшей из двух колод) или **другой изучаемый язык** — предупредить, что это, возможно, другая колода с тем же `id`, и спросить, устанавливать ли (Р18). Колода, в которую добавили много новых записей, предупреждения не вызывает: старые записи в ней остались.
5. Обновление по `id` записей:
   - запись есть в новой редакции — содержимое и `position` обновляются, `hidden = 0` (в том числе если она была скрыта и вернулась — прогресс вернётся вместе с ней);
   - записи нет в новой редакции — `hidden = 1`, содержимое прежнее, прогресс и журнал не трогаются;
   - аудио колоды заменяется целиком.
6. Журнал при импорте **не меняется никогда**. Карточки при обновлении не меняются; при установке колоды, которой нет (впервые или после удаления), её карточки пересчитываются из журнала (Р34) — прогресс удалённой колоды возвращается.

## Удаление колоды (Р34)

`deleteDeck` (`src/platform/repo.ts`) одной транзакцией удаляет строку `decks`, все записи колоды (и скрытые), её звук в `media` и её карточки в `cards`. Журнал не трогается (Р10): знакомства и ответы остаются, поэтому при повторной установке карточки пересчитываются из журнала (те же сроки), а знакомство с уже знакомыми записями не повторяется. Знакомства и ответы дня удаления продолжают считаться в дневных лимитах.

Импорт сообщает итог: сколько записей добавлено, обновлено, скрыто, вернулось.

Чтобы браузер не стёр базу при нехватке места, после каждого импорта и восстановления приложение просит постоянное хранилище (`navigator.storage.persist()`, Р18); в Chrome браузер решает сам, без вопроса пользователю. Состояние видно в Настройках, там же кнопка «Запросить постоянное хранилище».

## Резервная копия журнала (Р18)

- **«Сохранить журнал в файл»** — JSON-файл `mana-journal-ГГГГ-ММ-ДД.json`: `{"format": "mana-journal", "version": 1, "exportedAt", "userId", "deviceId", "records": [...]}`. В нём все записи журнала этого пользователя. Колоды и аудио в файл не входят: их восстанавливают повторным импортом ZIP.
- **«Восстановить из файла»** — только добавляет записи: UUID, которые уже есть, пропускаются. Затем карточки пересчитываются из журнала. Всё в одной транзакции.
- Файл проверяется целиком: если хоть одна запись не читается, ничего не добавляется.
- Файл принадлежит одному пользователю (`userId`). **Без входа:** если журнал на этом устройстве пуст (новая установка или после очистки данных), устройство принимает пользователя из файла и восстанавливает его прогресс; если здесь уже есть свои ответы другого пользователя, восстановление отказывается. **Со входом (6а.4, Р40 п. 11):** файл с id аккаунта или прежним номером установки принимается — записи встают под id аккаунта, имеющиеся UUID пропускаются, новые — в очередь отправки (`pullFirst`); файл неизвестного `userId` — после подтверждения на экране, и сервер делает этот `userId` прежним номером аккаунта (нужна сеть).

## Очередь отправки `outbox` (этап 6а.3, Р39)

Ключ `id`. Индекс `[status+queuedAt]`. Версия схемы 2 — только эта таблица.

| Поле | Тип | Что это |
|---|---|---|
| `id` | string | UUID записи в `log` |
| `status` | `'pending' \| 'rejected' \| 'conflict'` | `pending` — ждёт отправки; `rejected` / `conflict` — сервер не принял: остаётся здесь и в файле журнала, сама повторно не отправляется |
| `reason` | string? | почему не принята (`future`, `past`, `schema`, `size`, `user`, `conflict`) |
| `queuedAt` | number | порядок отправки — время записи, мс |

- В очередь попадает запись, сделанная на этом устройстве со входом, с `userId` аккаунта — **в той же транзакции**, что запись журнала (`recordIntro`, `recordReview`, `recordDrill`). С 6а.4 (Р40 п. 10) — ещё записи аккаунта, добавленные переносом, повторным входом и восстановлением файла со входом (порядок — время записи). Полученные с сервера записи сюда не попадают; полученная запись с тем же каноническим JSON, что у ожидающей здесь, уходит отсюда (сервер её хранит).
- **Статус отправки — только здесь.** Запись журнала не меняется никогда: её канонический JSON (`src/core/journalRecord.ts`) — то, что сервер хранит и хэширует; любое изменение дало бы `conflict` при повторе.
- `stored` и `duplicate` удаляются отсюда после ответа сервера. После выхода из аккаунта очередь остаётся, новые записи в неё не встают.
- Файл журнала — все записи, в том числе непринятые; формат файла не меняется.

**Получение** — одной транзакцией: новые записи в `log` (уже имеющиеся UUID пропускаются), `meta.sync.cursor`, пересчёт затронутых карточек по всей их истории, настройки. Записи колоды, которой на устройстве нет, хранятся, их карточки пересчитываются, но не выдаются.

**Обновление схемы.** Dexie 4 при `versionchange` (другое окно открыло новую версию) сам закрывает старое соединение; приложение вдобавок показывает экран «нужна новая версия». Проверено на fake-indexeddb: база версии 1 открывается новой версией со всеми строками; старый код (версия 1) открывает базу версии 2 без `VersionError` (`src/platform/db.test.ts`). Как это ведёт себя в Chrome на телефоне — проверяется на телефоне.

## Что не хранится

- Журнал и настройки прототипа (`localStorage`) не переносятся; экран прототипа работает с ними как раньше, отдельно.
- Исходный ZIP не хранится — только разобранные записи и аудио.
- Удаления колоды пока нет (не входит в 4.1).
- Скрытые записи на экране колоды не показываются; показывается их число.

## Синхронизация (этап 6а.3, Р39)

- Журнал: объединение по `id` (UUID); записи не меняются. Тот же UUID с другим содержимым — `conflict` на сервере, запись остаётся в `outbox` с этой причиной.
- `cards`: затронутые пары пересчитываются из журнала (`rebuildCards` по истории пары). Ответ, сделанный раньше уже учтённого в карточке, тоже пересчитывает её.
- `settings`: три ключа; побеждает изменение, которое сервер получил последним.
- Размеры обмена (27.10.2026, Р43): отправка — пачками по 25 записей (сервер принимает до 100), при ошибке пачка делится 25 → 13 → 10; получение и выгрузка журнала — страницами по 200 (больший `limit` сервер урезает), при ошибке страница делится 200 → 100 → 50, следующая — снова 200.
- Колоды: пока не синхронизируются (6б).
- `userId`: при входе — `id` аккаунта (6а.2); перенос ответов со своим `userId` — раздел ниже (6а.4).

## Перенос ответов в аккаунт (этап 6а.4, Р40)

- **Первое устройство** (приглашение `account`): аккаунт получает его `userId`; записи не меняются, все встают в `outbox`.
- **Следующее устройство со своими ответами** (ссылка восстановления, код привязки): после ответа сервера одной транзакцией (`adoptAccount`) записи `log`, карточки `cards` (ключ с `userId`: удаление и вставка тех же строк; если у аккаунта такая карточка уже есть — пересчёт из объединённой истории) и строка `settings` локального пользователя и всех прежних номеров переходят на id аккаунта; меняется только `userId`. `meta`: `userId`, `account`, `formerUserIds`, `sync` с курсором 0 и `pullFirst`; `pendingTransfer` снимается. Все записи аккаунта, которых нет в `outbox`, встают туда. Повтор ничего не меняет.
- Где ещё хранится `userId`: нигде — во вложенных полях записей его нет; `outbox` и `meta.sync` его не содержат; в `sessionStorage` — только отметка перезагрузки, в `localStorage` — ключи прототипа.
- Запись, которую другое окно пишет с устаревшим прежним номером, сохраняется под id аккаунта; записи, оставшиеся под прежним номером (старая сборка), при запуске переносятся и встают в очередь.
- Критерий приёмки — сроки карточек до и после переноса совпадают: страница `#/lab/cards` (SHA-256 строк `deckId|entryId|skill|due`).

## Тесты

`src/core/deckImport.test.ts`, `src/core/cards.test.ts` — чистая логика; `src/platform/repo.test.ts` — база на fake-indexeddb:

- первый запуск создаёт `userId` и `deviceId` (UUID), повторный — не меняет;
- импорт: установка; новая редакция (обновление, скрытие, возврат записи, замена аудио); та же и старая редакция (вопрос); колода с другим составом или языком (предупреждение); колода с ошибками и не-ZIP ничего не меняют; ошибка посреди записи оставляет прежнюю редакцию целиком;

- пересчёт из журнала даёт те же карточки и те же даты `nextDue`, что пошаговая запись (и с выключенным, и с включённым «fuzz»);

## Решения владельца продукта по схеме (11.10.2026, Р18)

1. Первый запуск — три кнопки «Тоҷикӣ / Русский / English»; язык значений по умолчанию тот же.
2. Та же редакция при повторном импорте — вопрос «Переустановить?»; журнал не трогается.
3. Резервная копия: «Сохранить журнал в файл» и «Восстановить из файла» (добавление с пропуском существующих UUID); запрос `navigator.storage.persist()`.
4. Пересчёт FSRS из журнала проверен на детерминизм; в записи ответа хранится рассчитанная дата следующего повторения; тест сравнивает даты.
5. Уникальный id колоды по правилу «язык-тема-номер» (`DECK_PROMPT.md`, `DECK_FORMAT.md`); при импорте — предупреждение, если колода с тем же id сильно отличается по составу.
