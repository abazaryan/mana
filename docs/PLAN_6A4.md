## 1. API

### 1.1. Как сервер ведёт себя сейчас при повторном входе того же `deviceId` [Ф]

`worker/auth.ts`: `deviceOwner` возвращает `user_id` строки `devices`. В `redeem` (приглашение `device`) и `pair`: если владелец — тот же аккаунт, проверка проходит; `upsertDevice` делает `INSERT … ON CONFLICT (id) DO UPDATE SET name, last_seen_at, app_version, revoked_at = NULL WHERE devices.user_id = excluded.user_id` — строка устройства та же, отзыв снимается, создаётся новая сессия. Если владелец — другой аккаунт, `409 device_taken`. Приглашение `account` всегда создаёт новый случайный `userId` (`crypto.randomUUID()`), поэтому уже зарегистрированный `deviceId` там всегда даёт `409 device_taken`. Клиент на `device_taken` берёт новый `deviceId` (`renewDeviceId`) — только при пустом журнале, иначе исключение (`src/platform/repo.ts`).

### 1.2. Погашение приглашения `account` (`POST /api/auth/redeem`)

Новое необязательное поле `localUserId`. Нет поля — как в 6а.3 (случайный id; устройство без ответов).

С полем:
- формат: UUID **строчными буквами** (`/^[0-9a-f]{8}-…$/` без флага `i`; в записях id уже строчный — проверено на файле журнала телефона [Ф]). Иначе `400 bad_request`. Регистр не меняется: id аккаунта должен совпасть со строкой в записях байт в байт;
- аккаунт создаётся с `id = localUserId`, если его нет в `users.id` и в `user_aliases.alias_id`; иначе `409 user_taken`;
- **гонка закрыта условием в первой инструкции пачки** [Р]: `UPDATE invites SET used_at… WHERE token_hash = ? AND used_at IS NULL AND expires_at > ? AND NOT EXISTS (SELECT 1 FROM users WHERE id = ?L) AND NOT EXISTS (SELECT 1 FROM user_aliases WHERE alias_id = ?L) RETURNING kind`. Если id занят — приглашение не помечается, все остальные инструкции (они условны по `redeem_id`, как сейчас) ничего не делают, ответ `409 user_taken` (повторное чтение, чтобы отличить от `invalid`). Пачка D1 — одна транзакция [П: [D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch): «Batched statements are SQL transactions»; Ф: проверено в 6а.3 триггером посреди пачки]. Последняя страховка — `PRIMARY KEY users.id` и `UNIQUE alias_id`: ошибка ограничения → откат пачки → `409 user_taken` (ловится, не 500).
- порядок проверок: формат → `user_taken` → `device_taken` (п. 5: «устройство было в другом аккаунте» должно дать `user_taken`).

### 1.3. Приглашение `device` (ссылка восстановления) и код привязки (`POST /api/auth/pair`)

Новое необязательное поле `formerUserId` (тот же формат). Клиент шлёт его, только если на устройстве есть ответы; в нём — `meta.userId`. Аккаунт `A` известен серверу (приглашение или код).

| `formerUserId` = L | Ответ сервера | Запись |
|---|---|---|
| L = A | повторный вход, 200 | нет |
| L — уже прежний id аккаунта A | 200 (идемпотентно) | нет |
| L — `users.id` другого аккаунта или прежний id другого аккаунта | `409 user_taken`; код / приглашение **не тратятся**; в `pair` неудачная попытка **не считается** (код верный) | нет |
| L нигде не встречается | 200 | `user_aliases (A, L, now)` в той же пачке, условно по `redeem_id` / `used_device_id` |

Гонка — так же, условием в первой инструкции (`UPDATE invites …` / `UPDATE pairing_codes … AND NOT EXISTS (… users WHERE id = ?L AND id <> ?A) AND NOT EXISTS (… user_aliases WHERE alias_id = ?L AND user_id <> ?A)`), затем `INSERT … ON CONFLICT (user_id, alias_id) DO NOTHING`; `UNIQUE alias_id` — страховка.

Ответы `redeem`, `pair` дополняются `formerUserIds: string[]`.

### 1.4. Новый маршрут для файла с неизвестным `userId`

`POST /api/auth/alias {aliasId}` — `withSession`, `mutating` (**426** для старых сборок), тело `SMALL_BODY_LIMIT`. Те же четыре случая, что в таблице 1.3; ответ `200 {formerUserIds}`; повтор — 200. Ошибки: `400 bad_request`, `401`, `403 consent_required`, `409 user_taken`, `426`.

### 1.5. Согласие (Р39 п. 18)

Предлагаю **требовать согласие текущей версии** для любой записи в `user_aliases` (маршрут alias, перенос в `redeem device` и `pair`) [Р]: это новые данные аккаунта, связанные с журналом; без согласия журнал всё равно не принимается, и прежний id без журнала не нужен. Проверка — та же `hasConsent` из `worker/sync.ts` (вынести в общий файл). Для приглашения `account` согласие приходит в том же запросе — отдельной проверки не нужно. Без согласия — `403 consent_required`, ничего не тратится. До 6а.5 это касается только тестовых аккаунтов со старой версией.

### 1.6. `MIN_CLIENT` (ответ Г)

Новые поля необязательны; без них `redeem` / `pair` ведут себя как в 6а.3 — тест на тело запроса сборки 6а.3 (`{token, device, consent}` и `{code, device}`) [Р]. Маршрут alias старые сборки не вызывают. **Сам по себе 6а.4 подъёма не требует.** Но при варианте 0.1 (а) `MIN_CLIENT` поднимается из-за новой версии уведомления (Р39 п. 5).

### 1.7. `/api/auth/me`

Дополняется `formerUserIds` (п. 3). Согласие не проверяет (маршрут входа, как сейчас).

## 2. Миграция 0004

```sql
-- Migration 0004 (stage 6a.4, R40): earlier local userIds of an account (STAGE6_RESEARCH 4.1,
-- 5.9). An installation whose answers were added to the account under another id, or a backup
-- file of such an installation. alias_id is never a users.id and belongs to one account only.
CREATE TABLE user_aliases (
  user_id TEXT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  alias_id TEXT NOT NULL UNIQUE,
  added_at INTEGER NOT NULL,
  PRIMARY KEY (user_id, alias_id),

```

- Поля — как в `STAGE6_RESEARCH` 4.1; `added_at` — для администратора и разбора. Отдельный индекс по `user_id` не нужен: первичный ключ начинается с него [Р].

- Каскад к `users`: удаление аккаунта (6а.5) стирает и прежние id. D1 включает внешние ключи по умолчанию [П: [D1 foreign keys](https://developers.cloudflare.com/d1/sql-api/foreign-keys/)].
- Тесты: `worker/migrations.test.ts` (таблица STRICT, каскад, UNIQUE, CHECK). Сначала `--local`, затем команда `--remote` владельцу дословно.
- `tools/admin/users.ts` — добавить число прежних id у аккаунта (только чтение).

## 3. Как прежние `userId` доходят до других устройств

Через **`GET /api/auth/me`**, не через `pull` [Р]: `pull` — горячий путь, а список меняется редко. Устройство хранит **`meta.formerUserIds`** (имя из `STAGE6_RESEARCH` 5.10).
- обновляется: при входе (ответ `redeem` / `pair`), при тихом `whoAmI` на запуске (он уже есть — `src/ui/MainApp.tsx`), после маршрута alias и **свежим запросом перед восстановлением из файла**;
- без сети восстановление пользуется сохранённым списком: файл с id аккаунта или известным прежним id принимается и офлайн; с неизвестным — строка «нужен интернет».

## 4. Переписывание на устройстве

Где хранится `userId` [Ф, по коду]:
- `log` — верхнее поле записи (`LogBase.userId`); во вложенных полях (`fsrs`, `echo`, `copy`, `reviewId`) его нет; индексы `[userId+at]`, `[userId+deckId+entryId+skill+at]`, `[userId+deckId+entryId+type]`;
- `cards` — первичный ключ `[userId+deckId+entryId+skill]`;
- `settings` — первичный ключ `userId`;
- `meta.userId`, `meta.account.userId`; `meta.sync` — без `userId` (курсор, номера настроек);
- `outbox` — без `userId` (только id записи);
- `sessionStorage` — только отметка перезагрузки (`UpdateScreen.tsx`), `localStorage` — `sluh.*` прототипа; `userId` там нет;
- в памяти — `actor` и `boot.meta` в React; файл журнала (`exportJournal`) берёт `actor.userId`.

**Одна транзакция Dexie** `adoptAccount(db, A, L)` по `meta, settings, log, cards, outbox` [Р]:
1. все записи `log` с `userId = L` → та же запись с `userId = A` (`put` по тому же `id`; остальные поля, в том числе `deviceId`, время, UUID — без изменений);
2. `cards` с `userId = L`: удалить и вставить те же строки с `userId = A` (без пересчёта — сроки не меняются по построению; тест дополнительно сверяет с `rebuildCards`);
3. `settings`: строка L → A, если строки A нет; если есть — строка L удаляется;
4. `meta`: `userId = A`, `account = {A, …}`, `formerUserIds += L`, `sync` сбрасывается (курсор 0, как `markSignedIn`), снимается отметка `pendingTransfer` (п. 6);
5. `outbox`: `pending` для каждой записи `A`, которой там нет (`queuedAt = at`).

Новая схема Dexie не нужна: `formerUserIds` и `pendingTransfer` — поля строки `meta`, индексы не меняются [Р].

**Канонический JSON одинаков на любом устройстве** [Р]: меняется одна строка `userId`, порядок ключей канонический JSON сортирует. Тест: два устройства с одной и той же записью L переписывают её на A → SHA-256 канонического JSON одинаков и равен хэшу записи, созданной сразу с `userId = A`.

**Запись поверх устаревшего `actor`** (другая вкладка, ещё не знающая о переносе): `recordIntro` / `recordReview` / `recordDrill` берут `userId` из `meta` внутри своей транзакции, а не из памяти; запись с прежним id переписывается на `meta.userId`. Плюс проверка при каждом запуске: записи с `userId` из `meta.formerUserIds` → `adoptAccount` (идемпотентно, один запрос по индексу) — это ловит и вкладку старой сборки. Другие окна узнают о переносе через тот же `BroadcastChannel` (`syncEvents.ts`) и перезагружают данные.

## 5. Исключение из «запись журнала не меняется»

Переписываются **только записи, которые никогда не уходили на сервер** [Р]. Гарантия:
- в очередь (и на сервер) попадает только запись с `userId` = аккаунт сессии (`enqueue`, `checkPushed` — `user`) [Ф];
- id аккаунта на сервере — либо случайный серверный, либо перенесённый локальный; прежний id (`alias`) никогда не бывает `users.id` и наоборот (условия 1.2–1.4); значит записей с `userId = L` на сервере нет, если сервер разрешил L как прежний id [Р];
- устройство переписывает **только после ответа сервера**, разрешившего L (или L = A — тогда переписывать нечего);
- дополнительная проверка на устройстве: если в `outbox` есть строка записи с `userId = L`, перенос отменяется с ошибкой (такого быть не должно).

Исключение: L — id **удалённого** аккаунта (6а.5). Сервер его уже не знает и примет как прежний id; записи с L на сервере стёрты вместе с аккаунтом — переписывание ничему не противоречит [Р].

**Устройство было в другом, ещё существующем аккаунте A1** (его `meta.userId = A1`, часть записей уже на сервере): сервер отвечает `409 user_taken` (порядок проверок 1.2), ничего не меняется, строка `transfer.userTaken`: войти в прежний аккаунт или сохранить журнал в файл и очистить данные сайта. `device_taken` при ответах на устройстве (редкий случай: устройство было в A1 с пустым журналом, потом восстановило чужой файл) — предлагаю взять новый `deviceId` и для устройства с ответами: старые записи сохраняют прежний `deviceId`, на сервере у `deviceId` в записях внешнего ключа нет [Ф: `migrations/0003_sync.sql`] [Р].

`DATA_MODEL.md` и Р40 записывают исключение словами: «запись журнала не меняется, кроме одного раза — смены `userId` до первой отправки при переносе (Р40)».

Шаги второго устройства: (1) вопрос → «Бале»; (2) **транзакция: `meta.pendingTransfer = {formerUserId: L, at}`**; (3) запрос `pair` / `redeem`; (4) ответ сервера (cookie + alias); (5) `adoptAccount`; (6) отправка очереди.

Для приглашения `account` повтор новой `account`-ссылкой даст `user_taken` — нужна ссылка восстановления `recover.ts` (L = A, повторный вход). Известное ограничение, как потерянный ответ в 6а.2 |

## 7. Очередь

- Перенесённые и восстановленные записи встают в `outbox` (расширение Р39 п. 6: «в очередь — записи этого устройства со входом» + «записи `userId` аккаунта, добавленные переносом, повторным входом или восстановлением файла»).
- Порядок — `queuedAt = at` записи: старые уходят первыми, по времени — так другие устройства пересчитывают карточки с меньшим числом повторных пересчётов [Р].
- Пачки — как в 6а.3: 100 записей, ≤ 512 КиБ, 2 с между пачками.
- **472 записи** [Р]: файл телефона 570 334 байт на 459 записей [Ф] → ≈ 1,2 КБ на запись → пачка 100 ≈ 120 КБ; 5 отправок, 4 паузы → ≈ 10–15 с; затем получение — 1 страница (свои записи пропускаются).
- **Повторный вход (ответ Б).** В очередь — все записи `userId` аккаунта, которых нет в `outbox`. Оценка [Р]:
  - как есть (отправить всё, сервер ответит `duplicate`): 500 записей — 5 отправок ≈ 10–15 с; 20 000 — 200 отправок ≈ 7–10 мин и ≈ 24 МБ вверх (плюс 40 страниц получения после курсора 0);
  - **предлагаю «сначала получить» после повторного входа и восстановления файла**: отметка `meta.sync.pullFirst`; движок сначала получает всё с курсора 0, и запись, пришедшая с сервера **с тем же каноническим JSON**, уходит из `outbox` (раз сервер её прислал, она там есть; иное содержимое остаётся в очереди и честно получит `conflict`). Итог: 500 — 1 страница, 0 отправок, ≈ 1–2 с; 20 000 — 40 страниц ≈ 1–2 мин, 0 отправок. Для первого устройства (сервер пуст) — одна пустая страница.
- CPU пачки 100 записей на настоящем сервере — открытый пункт 6а.3, проверяется в 6а.6 (телефон, 472 записи).

**«Сначала получение» — как устройство узнаёт, что сервер уже имеет** (принято владельцем 25.10.2026) [Р]:
1. Перенос, повторный вход и восстановление файла со входом одной транзакцией ставят записи аккаунта в `outbox` (`pending`), сбрасывают курсор в 0 и ставят отметку `meta.sync.pullFirst`.
2. Пока отметка стоит, движок **не отправляет ничего** (и `keepalive` при уходе в фон тоже): только получает страницы с курсора.
3. Каждая страница — одна транзакция: новые записи, курсор и **сверка очереди**. Запись пришла с сервера, а у устройства есть запись с тем же `id` и строкой `pending` в `outbox`: канонический JSON (`canonicalJson`) обеих совпал — строка уходит из `outbox` (сервер её хранит, отправка дала бы `duplicate`); не совпал — строка остаётся и при отправке честно получит `conflict`. Запись, которой нет в полученных страницах, сервер не имеет: сервер отдаёт все записи аккаунта по `seq`, курсор 0 — значит, после последней страницы (`more: false`) в очереди остаётся ровно то, чего на сервере нет.
4. Последняя страница в той же транзакции снимает `pullFirst`; дальше обычная отправка остатка.
5. **Получение прервалось посередине** (сеть, закрытая вкладка, ошибка): транзакции прошедших страниц сохранены вместе с курсором и вычеркнутыми строками очереди; отметка стоит. Следующий запуск продолжает получение с сохранённого курсора, отправки до конца получения нет. Ничего не отправляется дважды сверх обычного: вычеркнуты только записи, которые сервер точно прислал; недошедшая страница не сохранила ничего (Р39 п. 8). Худший случай — повтор одной страницы.
6. Новые ответы, сделанные во время этого получения, встают в очередь как обычно и уходят после него.

Тесты: сервер уже имеет часть записей → после получения в очереди только остальные, отправка — только `stored`; запись с тем же `id` и другим содержимым → остаётся, `conflict`; обрыв после каждой страницы → продолжение с курсора, итог тот же; во время `pullFirst` отправки нет (и `sendBeforeLeaving` молчит).
