## Коротко

- **Бесплатного тарифа хватает на запросы и операции**, но **предел — размер базы D1: 500 МБ** на бесплатном тарифе [П]. Журнал ≈ 1 КБ на запись [Ф]. При реальной нагрузке (≈ 46 записей в день у Pooya [Ф], 20 человек) — около года; при верхней оценке (300 в день у каждого из 20) — ≈ 80 дней [Р]. Workers Paid ($5/мес) даёт 10 ГБ на базу [П] — это и есть переход по Р11.
- На бесплатном тарифе превышение **останавливает** API до 00:00 UTC (статические файлы сайта продолжают открываться), на Paid — **выставляется счёт без потолка**, предупреждения о расходах только информируют [П].
- Юрисдикция `eu` у D1 гарантирует хранение и выполнение запросов D1 в ЕС, у R2 — хранение объектов в ЕС; **сам Worker выполняется в ближайшем к пользователю дата-центре**, гарантия места — только в Enterprise [П].
- Вход — **своя реализация на Web Crypto** (непрозрачные токены, в базе только SHA-256), без новых зависимостей [Р]; готовые библиотеки — раздел 3.
- Синхронизация — пачки, курсор по серверному номеру, идемпотентность по UUID, пересчёт FSRS на клиенте; при первом входе аккаунт получает `userId` телефона, записи не переписываются [Р].
- Второй аккаунт на устройстве позже — отдельной базой IndexedDB на аккаунт и cookie на профиль; в 6а закладываются только заголовок профиля и имя cookie (5.11) [Р].

- Личные колоды без сервера (проверка с отчётом для ИИ, импорт `deck.json`, голос браузера по записи) можно делать **до 6а** [Р].

## 1. Cloudflare

### 1.1. Что изменится, когда к статическому Worker добавится API

- Сейчас — только статика, без кода Worker (`wrangler.jsonc`: нет `main`, `not_found_handling: "none"`) [Ф].
- `assets.run_worker_first` принимает `true` / `false` или массив шаблонов; `!` в начале — исключение, исключения главнее; до 100 шаблонов [П: [Static Assets binding](https://developers.cloudflare.com/workers/static-assets/binding/), [configuration](https://developers.cloudflare.com/workers/wrangler/configuration/)]. Для нас — `["/api/*"]` [Р].
- **Платные (лимитные) запросы — только к коду Worker:** «Requests to static assets are free and unlimited»; запросы, подходящие под `run_worker_first`, всегда вызывают Worker и считаются его запросами [П: [billing and limitations](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/), [pricing](https://developers.cloudflare.com/workers/platform/pricing/)]. Значит, лимитными станут только `/api/*` [Р].
- Запрос не-навигации (например, `fetch`) по пути, которого нет среди файлов, вызывает Worker и без `run_worker_first` [П: [SPA routing](https://developers.cloudflare.com/workers/static-assets/routing/single-page-application/)]. Как ведёт себя массив `run_worker_first` вместе с `not_found_handling: "none"` для прочих путей, документация **не говорит** [П] — проверить после первого развёртывания (`curl /nope` → прежний 404, Worker не вызван) [Р].
- Флаг `assets_navigation_prefers_asset_serving` — по умолчанию с 2025-04-01: навигация обслуживается файлами раньше Worker [П: [compatibility flags](https://developers.cloudflare.com/workers/configuration/compatibility-flags/)]. На `/api/*` (не навигация, `fetch`) не влияет [Р].
- **`_headers` к ответам кода Worker не применяется** — «even if the request URL matches a rule» [П: [headers](https://developers.cloudflare.com/workers/static-assets/headers/)]; это уже записано в Р32 п. 6 [Ф]. Заголовки API — в коде (7.5).

| CPU на запрос | **10 мс** | до 5 мин (по умолчанию 30 с); 30 млн CPU-мс в месяц включено |
| Подзапросы | 50 | 10 000 |

| Размер Worker | 64 МиБ | 64 МиБ |

- **Превышение на Free:** лимит сбрасывается в 00:00 UTC; документация лимитов говорит об ошибке 1027, страница о статике — что запросы по `run_worker_first` получат 429, а файлы сайта будут отдаваться дальше [П, **источники расходятся** в коде ошибки]. Для нас: `/api/*` недоступен, сайт открывается, занятия идут локально, синхронизация догонит позже [Р].
- **10 мс CPU** — главный риск Free для нашего кода [Р]: время ожидания базы в CPU не входит, но разбор JSON пачки, SHA-256 и особенно проверка ZIP (6б) — входят. Пачка 200 записей ≈ 200 КБ JSON — скорее всего укладывается (не замерено); проверка архива 20 МБ — вероятно, нет.

### 1.3. D1

[D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/) [П]:

| | Free | Paid |
|---|---|---|
| Размер базы | **500 МБ** | 10 ГБ |
| Хранение на аккаунт | 5 ГБ | 1 ТБ; 5 ГБ включено, далее $0,75 за ГБ-мес |
| Чтение строк | 5 млн в сутки | 25 млрд в месяц включено, далее $0,001 за млн |
| Запись строк | 100 000 в сутки | 50 млн в месяц включено, далее $1 за млн |
| Запросов на вызов Worker | 50 | 1 000 |
| Баз на аккаунт | 10 | 50 000 |
| Time Travel (восстановление по времени) | **7 дней** | **30 дней** |

- Одинаково на обоих: запрос до 100 КБ, до 100 параметров, строка или значение до 2 МБ, запрос до 30 с [П].
- **Как считаются строки:** чтение — просмотренные строки, а не возвращённые (полный просмотр таблицы 5 000 строк = 5 000); индекс уменьшает чтение, но каждая запись в индексированный столбец добавляет запись строки; размер строки не важен [П]. В ответе каждого запроса — `rows_read` / `rows_written`: по ним считать нагрузку в тестах на настоящей базе [Р].
- **Превышение на Free:** запросы к D1 не выполняются до 00:00 UTC; при пределе хранения — нельзя вставлять, пока не освободить место [П]. Не счёт, а остановка.
- **Time Travel** включён всегда и бесплатно; восстановление `wrangler d1 time-travel restore` перезаписывает базу целиком (с закладкой для отмены) [П: [Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)].
- **Юрисдикция:** `eu` — база «only run and store data within a region» (выполнение запросов D1 и хранение); доступ к базе не ограничен — Worker из любой точки может обращаться к ней; **юрисдикцию нельзя добавить или изменить после создания**; команда `wrangler d1 create <имя> --jurisdiction=eu`; подсказки места (`weur`) — не гарантия; при юрисдикции реплики чтения — только внутри неё [П: [data location](https://developers.cloudflare.com/d1/configuration/data-location/)].
- **Миграции:** `wrangler d1 migrations create` / `apply`, папка `migrations/`, применённые — в таблице `d1_migrations`; флаги `--local` / `--remote`; какой флаг по умолчанию, документация **не говорит** — всегда писать `--remote` явно [П: [migrations](https://developers.cloudflare.com/d1/reference/migrations/)].
- Чтение с реплик (Sessions API) включается отдельно; нам не нужно [П/Р].

### 1.4. R2

[R2 pricing](https://developers.cloudflare.com/r2/pricing/), [R2 limits](https://developers.cloudflare.com/r2/platform/limits/), [data location](https://developers.cloudflare.com/r2/reference/data-location/) [П]:

- Бесплатно в месяц: 10 ГБ-мес хранения, 1 млн операций класса A (запись, список), 10 млн класса B (чтение); исходящий трафик бесплатный. Сверх — $0,015 за ГБ-мес, $4,50 за млн A, $0,36 за млн B; удаление бесплатно. Превышение **оплачивается**, R2 не останавливается [П].
- Нужна **подписка R2** в аккаунте (оформляется через оплату) [П: [get started](https://developers.cloudflare.com/r2/get-started/)]; нужна ли карта, официально **не сказано**; сторонние руководства пишут, что нужна карта или PayPal [П: [tech-insider.org](https://tech-insider.org/au/how-to-set-up-cloudflare-r2-2026/)]. Это решение Pooya до 6б.
- Юрисдикция `eu` «guarantee[s] objects … stored within a specific jurisdiction»; после создания корзины не меняется; привязка в `wrangler.jsonc` требует `"jurisdiction": "eu"`; команда `wrangler r2 bucket create <имя> --jurisdiction eu` [П: [wrangler r2](https://developers.cloudflare.com/workers/wrangler/commands/r2/)].
- Объект одним запросом — до 5 ГиБ; запись в один ключ — не чаще 1 раза в секунду; через Worker — в пределах тела запроса Worker (100 МБ) [П]. Колоду 20 МБ передавать потоком в `R2.put()`, не держа в памяти целиком [Р].

### 1.5. Где выполняется Worker и что гарантирует `eu`

- Worker выполняется «in a data center closest to where the request was received»; Smart Placement и `placement.region` — для скорости, без обязательства о месте [П: [placement](https://developers.cloudflare.com/workers/configuration/placement/)].
- Выполнение Worker и TLS в выбранном регионе — Regional Services, «an Enterprise add-on»; Data Localization Suite — только Enterprise [П: [Regional Services](https://developers.cloudflare.com/data-localization/regional-services/)].
- **`eu` НЕ гарантирует** [Р, по источникам выше]: где расшифровывается запрос и работает код Worker (тело запроса, ответы ученика в пути), где хранятся логи Workers (если включить), кто может обращаться к базе. Для пользователя в Европе ближайший дата-центр, скорее всего, в Европе, но это не обещание. Гарантировано: данные D1 (хранение и запросы) и объекты R2 — в ЕС.
- В уведомлении (раздел 8) так и писать: «хранятся в ЕС», а не «обрабатываются только в ЕС» [Р].

### 1.9. Отдельный токен сборки

- Workers Builds по умолчанию создаёт токен сам; можно выбрать свой (Settings → Build); поддерживаются только токены пользователя; рекомендуется один и тот же токен для всех публикаций Worker [П: [builds configuration](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/)].
- Права автоматического токена: Account Settings (чтение), Workers Scripts (правка), Workers KV (правка), Workers R2 (правка), Zone Workers Routes (правка), User Details и Memberships (чтение); **D1 — нет** [П, там же].
- Для публикации прав на привязанные ресурсы не нужно; для `d1 migrations apply --remote` нужно право D1 Edit [П: [authorization](https://developers.cloudflare.com/workers/authorization/workers/), [permissions](https://developers.cloudflare.com/fundamentals/api/reference/permissions/)].
- Изменённый или удалённый токен становится «stale» — создать новый и выбрать его в сборке [П: [troubleshoot](https://developers.cloudflare.com/workers/ci-cd/builds/troubleshoot/)]. Значит, **общий токен с Rechenwege нельзя менять без поломки сборки обоих** [Р].
- Предложение [Р]: перед первым кодом Worker Pooya создаёт токен «mana build token» (My Profile → API Tokens → Create) с правами: Account Settings Read, Workers Scripts Edit, User Details Read, Memberships Read, **D1 Edit — только если миграции идут в сборке**; ограничение — один аккаунт `amisipehr`. Затем Worker `mana` → Settings → Build → API token → выбрать его. Достаточность этого набора документация не подтверждает — проверить первой сборкой.
- **Миграции — не в сборке** [Р]: команда сборки остаётся `npm test && npm run build`, публикации — `npx wrangler deploy`; миграции применяю я вручную (`wrangler d1 migrations apply … --remote`) отдельным токеном администратора (7.1) **до** публикации кода, который их требует. Так токену сборки не нужно право D1, а ошибочная миграция не применится сама при push.

## 2. Сессии на одном origin

### 2.1. Cookie

Предложение [Р]: `Set-Cookie: __Host-mana_s=<токен>; Secure; HttpOnly; SameSite=Strict; Path=/; Max-Age=34560000` (400 суток).

- `__Host-` — браузер примет cookie, только если она `Secure`, установлена по HTTPS, без `Domain` и с `Path=/` [П: [MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)]; OWASP рекомендует этот префикс для сессий, `HttpOnly`, без `Domain`, `SameSite=Strict` («preferred») или `Lax` [П: [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)].
- **Strict, а не Lax** [Р]: при Strict переход по ссылке с другого сайта приходит без cookie [П: [web.dev](https://web.dev/articles/samesite-cookies-explained)], но нам это не мешает — HTML сессии не требует, а запросы `fetch('/api/…')` со страницы идут с того же сайта и cookie несут. Ссылка-приглашение тоже не зависит от cookie (3.1). Lax понадобился бы, только если бы сервер проверял сессию при открытии страницы. Отправляется ли Strict-cookie, когда ссылку открывает другое приложение Android (мессенджер), источники **не говорят** [П] — для нашей схемы не важно.
- **Срок.** Chrome урезает `Max-Age` / `Expires` больше 400 суток до 400 [П: [developer.chrome.com](https://developer.chrome.com/blog/cookie-max-age-expires)]. Cookie — 400 суток, обновляется ответом сервера не чаще раза в сутки. На сервере сессия истекает после **180 суток без запросов** (11.4, вопрос 3): эталонный код Lucia — 10 суток со скользящим продлением [П: [auth_session.ts](https://raw.githubusercontent.com/lucia-auth/lucia/main/code/auth_session.ts)], NIST для уровня AAL1 — повторный вход не реже 30 суток «SHOULD» [П: [SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html)]; но у нас повторный вход — это новая ссылка от администратора, и родственник, вернувшийся после каникул, не должен её ждать [Р].
- Токен — 32 случайных байта (`crypto.getRandomValues`), в base64url; в базе — только SHA-256 [Р; так же у Lucia — П, там же]. OWASP: не меньше 64 бит, свои идентификаторы — не меньше 128 [П].

### 2.2. Защита от CSRF

[Р] Для всех запросов, кроме GET / HEAD, к `/api/*`:

1. `Sec-Fetch-Site` должен быть `same-origin`; если заголовка нет — сравнить `Origin` с `https://mana.amisipehr.workers.dev`; нет обоих или `Origin: null` — 403. OWASP: `Sec-Fetch-Site` — «the primary signal», `Origin` — обязательный запасной путь, отсутствие заголовков — не признак своего запроса [П: [OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)]; так же в эталоне Lucia [П].
2. Тело — только `Content-Type: application/json` (чужая страница не отправит такой запрос без предварительной проверки CORS) [П: OWASP, там же].
3. Заголовков CORS нет вовсе; GET ничего не меняет.
4. `SameSite=Strict` — дополнительно; OWASP: SameSite «does not replace a proper CSRF defense» [П].

`Sec-Fetch-Site` — во всех современных браузерах с марта 2023 [П: [MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Sec-Fetch-Site)], в Safari — с 16.4 [П: [WebKit 16.4](https://webkit.org/blog/13966/webkit-features-in-safari-16-4/)].

### 2.3. Safari на iOS (iPhone пока нет)

- **7 суток:** ITP удаляет всё хранилище, записываемое скриптами (IndexedDB, localStorage, service worker и его кэш), после 7 дней использования Safari без взаимодействия с сайтом [П: [WebKit, 24.03.2020](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)]. Что считается «взаимодействием», пост **не определяет** [П].
- **Приложение на главном экране** — «not part of Safari and thus have their own counter of days of use»; «We do not expect the first-party in such a web application to have its website data deleted» [П, там же].
- **Cookie, выставленные сервером** (`Set-Cookie` в ответе), под 7-суточный предел не попадают — только созданные через `document.cookie` [П: [WebKit ITP 2.1](https://webkit.org/blog/8613/intelligent-tracking-prevention-2-1/)]. Исключения: CNAME на чужой домен [П: [WebKit 11338](https://webkit.org/blog/11338/cname-cloaking-and-bounce-tracking-defense/)] и ответы с «чужого» IP — другая подсеть, чем у страницы [П: [bug 246477](https://bugs.webkit.org/show_bug.cgi?id=246477), [PR 5347](https://github.com/WebKit/WebKit/pull/5347)]. У нас API и страница — один адрес, один IP: не должно касаться [Р, не проверено].
- **Safari и приложение на главном экране не делят хранилище и cookie** — «by design» [П: [bug 181849](https://bugs.webkit.org/show_bug.cgi?id=181849)]. Следствие: ссылку-приглашение, открытую в Safari, установленное приложение не увидит; на iPhone вход — **внутри установленного приложения**: поле «Вставить ссылку или код» на экране входа [Р].
- **Распознавание речи в установленном приложении на iOS, вероятно, не работает**: инженер WebKit, 2021 — «SpeechRecognition API is not available in SafariViewController and web apps added to Home Screen for now», ошибка закрыта как «LATER», подтверждения исправления нет [П: [bug 225298](https://bugs.webkit.org/show_bug.cgi?id=225298), [форум Apple, 2024](https://developer.apple.com/forums/thread/748048)]. В Safari — частичная поддержка с iOS 14.5 [П: [caniuse](https://caniuse.com/speech-recognition)]; нужна включённая Siri / диктовка — только по сторонним комментариям [П]. Значит, пользователю iPhone придётся заниматься во вкладке Safari — и там действует правило 7 суток; синхронизация 6а это смягчает: потерянная база восстановится с сервера [Р].
- `navigator.storage.persist()` в Safari 17 — решение по эвристике (например, открыт ли сайт как приложение) [П: [WebKit 14403](https://webkit.org/blog/14403/updates-to-storage-policy/)]; есть сообщение, что он всегда возвращал false [П: [bug 271401](https://bugs.webkit.org/show_bug.cgi?id=271401), состояние не проверено] — **источники расходятся**.
- Приложения на главном экране в ЕС: в бета-версиях iOS 17.4 убирали, затем Apple оставила [П, вторичный: [9to5mac](https://9to5mac.com/2024/03/01/apple-home-screen-web-apps-ios-17-eu/)]; первоисточник Apple **не найден**.

### 2.4. Android, установленное приложение, этап 7

- Установленное приложение (WebAPK) и Chrome — один профиль: cookie и IndexedDB общие, очистка данных Chrome касается и приложения [П: [web.dev WebAPKs](https://web.dev/articles/webapks)]; у Pooya приложение установлено как WebAPK [Ф — `docs/STATUS.md`]. Значит, вход во вкладке Chrome = вход в приложении [Р]. Ссылки внутри `scope` WebAPK открывает сам [П, там же] — ссылка-приглашение, скорее всего, откроется сразу в приложении [Р, проверить на телефоне].
- `id` манифеста — постоянный, `https://mana.amisipehr.workers.dev/` [Ф — Р32 п. 10]; cookie от него не зависят (они по адресу сайта) [Р]. Без service worker `Set-Cookie` и `fetch` работают как в обычной вкладке [Р].
- **Этап 7** [Р]: service worker не должен кэшировать `/api/*` (только статику) и не должен подменять ответы 401 / 426; офлайн-очередь отправки (5.4) уже готова к работе без сети; проверка «обновите приложение» (5.5) — через обновление service worker.
- `persist()` в Chrome — без вопроса, по эвристике: вовлечённость, установка, закладка [П: [web.dev](https://web.dev/articles/persistent-storage)]; у Pooya — «Доимӣ» [Ф].

## 3. Вход

### 3.1. Приглашение (новый аккаунт и первое устройство)

1. Pooya просит: «приглашение для N, до 16 — да/нет». Я запускаю скрипт `tools/admin/invite.ts` [Р; 3.6]. Скрипт создаёт 32 случайных байта, пишет в D1 только SHA-256, срок — **48 часов**, одно использование. Ссылка `https://mana.amisipehr.workers.dev/#/join/<токен>` кладётся **в буфер обмена Windows** и в файл в `tools/.out/` (вне git), в терминал не выводится; Pooya отправляет её сам.
2. Токен — во фрагменте `#…`: фрагмент не уходит на сервер при открытии страницы, не попадает в журналы и в `Referer` [Р; `Referrer-Policy: no-referrer` уже стоит — Ф]. Мессенджер, строящий предпросмотр ссылки, токена не погасит: погашение — только `POST` из приложения [Р]. OWASP для ссылок-токенов: случайность криптостойкая, одно использование, срок, хранение в защищённом виде, ограничение частоты, `no-referrer` на странице [П: [OWASP Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)].
3. Приложение открывает экран «Даъватнома»: уведомление о данных (раздел 8) → если в приглашении отмечено «до 16» или человек ответил «мне нет 16» — экран для родителя (имя, отметка согласия) → если на устройстве есть ответы — вопрос о переносе (5.9) → «Ворид шудан».
4. `POST /api/auth/redeem {token, deviceId, deviceName, localUserId, transfer, consent}` → сервер одной пачкой: находит приглашение по хэшу, проверяет срок и `used_at IS NULL`, ставит `used_at` (условием `WHERE used_at IS NULL` — второе погашение невозможно), создаёт `users`, `devices`, `consents`, `sessions` → `Set-Cookie` [Р].
5. Приложение убирает токен из адреса (`history.replaceState`) [Р].

### 3.2. Новое устройство

- **Код привязки с вошедшего устройства:** Настройки → «Иловаи дастгоҳ» → сервер выдаёт код из 8 знаков Crockford Base32 (40 бит), срок **10 минут**, одно использование, один действующий код на аккаунт. На новом устройстве: экран входа → «Код дорам» (кандидат; «рамз» в Иране — пароль, 8.6) → ввод → `POST /api/auth/pair` → новое устройство и сессия [Р]. Ориентиры: NIST — одноразовые секреты от 6 цифр, срок 10 минут, при < 64 бит — ограничить неудачные попытки, не больше 100 подряд [П: [SP 800-63B §3.1.3.2, §3.2.2](https://pages.nist.gov/800-63-4/sp800-63b.html)]; ASVS 5.0 — от 20 бит, срок до 10 минут, одно использование, ограничение частоты; секреты < 112 бит хранить алгоритмом для паролей [П: [ASVS V6](https://raw.githubusercontent.com/OWASP/ASVS/master/5.0/en/0x15-V6-Authentication.md)]. Код живёт 10 минут и защищён счётчиком попыток (7.3). ASVS требует для секретов < 112 бит медленный хэш для паролей; PBKDF2 есть в Web Crypto, но на Free у запроса 10 мс CPU (1.2) — число итераций придётся подобрать замером, иначе SHA-256 (код всё равно живёт 10 минут) [Р; противоречие требований, решу замером в 6а.2].
- **Или новая ссылка от администратора** — приглашение вида `device` для существующего аккаунта (тот же поток 3.1, без создания аккаунта).

### 3.3. Восстановление и отзыв

- **Потеряны все устройства:** скрипт `recover.ts` — ссылка `device` для аккаунта, по желанию с отзывом всех прежних устройств [Р].
- **Отзыв устройства:** Настройки → «Дастгоҳҳо» — список (имя, последний вход) → «Хуруҷ аз ин дастгоҳ» на любом своём устройстве; или скрипт `revoke.ts`. Отзыв = удаление сессий устройства; следующий его запрос — 401 [Р]. Журнал, присланный этим устройством раньше, остаётся.
- **Выход на своём устройстве** — удаляет сессию; локальные данные остаются (экран спрашивает, стереть ли их) [Р].

## 4. Схема D1 (только описание, без SQL-файлов)

Принцип [Р]: сервер хранит журнал как есть (тело записи — JSON, который прислал клиент) и несколько полей рядом для индексов и проверок. FSRS на сервере не считается — карточки остаются производными на клиенте (Р10, `docs/DATA_MODEL.md`) [Ф]. Время — целые миллисекунды UTC (`INTEGER`), идентификаторы — `TEXT` (UUID).

### 4.1. Аккаунты и вход (6а)

| Таблица | Поля | Ключи и индексы | Зачем |
|---|---|---|---|
| `users` | `id` (UUID — он же `userId` в записях журнала, см. 5.8), `label` (имя для администратора: «Мама»), `minor` (0/1 — отметка «до 16», дата рождения не хранится), `created_at` | PK `id` | аккаунт |
| `user_aliases` | `user_id`, `alias_id` (прежний локальный `userId` установки, чьи ответы перенесены), `added_at` | PK (`user_id`, `alias_id`); UNIQUE `alias_id` | восстановление из старого файла поверх своих ответов (5.9) |
| `invites` | `token_hash` (SHA-256 токена), `kind` (`account` — новый аккаунт / `device` — новое устройство существующего, это и есть ссылка восстановления), `user_id` (NULL у `account`), `label`, `minor`, `created_at`, `expires_at`, `used_at`, `used_device_id` | PK `token_hash`; индекс `expires_at` (чистка) | приглашение и восстановление |

### 4.2. Журнал и настройки (6а)

| Таблица | Поля | Ключи и индексы |
|---|---|---|
| `journal` | `seq` (`INTEGER PRIMARY KEY AUTOINCREMENT` — серверный порядковый номер, курсор), `user_id`, `id` (UUID записи), `type` (`intro` / `review` / `drill` / любой будущий), `at`, `device_id`, `deck_id`, `entry_id`, `rules` (NULL у записей без версии), `body` (JSON записи целиком, как пришёл), `body_hash` (SHA-256 канонического JSON, 5.2), `received_at` | PK `seq`; UNIQUE (`user_id`, `id`); индекс (`user_id`, `seq`) |
| `user_settings` | `user_id`, `key` (`uiLang`, `meaningLang`, `newPerDay`), `value` (JSON), `server_rev` (номер изменения), `updated_at` (время сервера), `device_id` | PK (`user_id`, `key`) |

- Все три типа записей журнала — одна таблица: общие поля (`id`, `type`, `at`, `deck_id`, `entry_id`, `device_id`) вынесены в столбцы, остальное — в `body` [Р]. Новые поля и типы записей не требуют миграции: сервер не знает их смысла и хранит как есть (5.5).
- UNIQUE (`user_id`, `id`), а не глобальный UNIQUE `id`: чужой UUID не даёт сведений о другом пользователе [Р].
- Курсор — `seq`, не время клиента (решение Pooya). В SQLite запись идёт в один поток, поэтому порядок `seq` совпадает с порядком фиксации: запись с меньшим номером не может появиться позже записи с большим [Р — свойство SQLite; если D1 когда-нибудь включит чтение с реплик, курсор останется верным, но записи будут приходить с задержкой]. Каждая пачка отправки — одна транзакция (`batch`).
- Размер: запись журнала сейчас ≈ 1 КБ (файл журнала 49 КБ на 48 записей, `docs/STATUS.md`) [Ф]; 300 записей в день × 20 пользователей × 365 дней ≈ 2,2 млн строк ≈ 2–3 ГБ в год [Р — оценка; сравнение с лимитами D1 — раздел 1].

### 4.3. Колоды (6б)

| Таблица | Поля | Ключи и индексы |
|---|---|---|
| `decks` | `owner` (`library` — общая библиотека администратора, либо `user_id` владельца личной колоды), `deck_id` (из `deck.json`), `language`, `title` (JSON), `current_revision`, `created_at`, `updated_at` | PK (`owner`, `deck_id`) — **`deck_id` уникален в пределах владельца** |
| `deck_revisions` | `owner`, `deck_id`, `revision`, `r2_key`, `bytes`, `sha256`, `entries`, `audio_files`, `check` (JSON отчёта проверки: число ошибок, предупреждений, сведений), `uploaded_at`, `uploaded_by_device` | PK (`owner`, `deck_id`, `revision`) |
| `library_choices` | `user_id`, `deck_id`, `added_at` | PK (`user_id`, `deck_id`) — какие колоды библиотеки выбрал пользователь (Р9) |
| `quotas` | `user_id`, `max_bytes`, `max_decks` | PK `user_id`; нет строки — значения по умолчанию (7.6) |

- Ключи R2: `library/<deck_id>/<revision>.zip`, `users/<user_id>/<deck_id>/<revision>.zip` [Р]: удаление аккаунта — удаление по префиксу `users/<user_id>/`.
- **Вопрос «одна запись в нескольких колодах — один комплект карточек?» (4.4б) схема не предрешает** [Р]: сервер не хранит «учебных единиц» и не связывает записи разных колод; журнал по-прежнему ссылается на пару `deck_id` + `entry_id`. Любое решение 4.4б (общий комплект по `text` + `form` или раздельный) принимается на клиенте при пересчёте.
- **Конфликт `deck_id` у одного пользователя** [Р]: запись журнала не говорит, библиотечная колода или личная, — только `deckId`. Поэтому у одного пользователя `deck_id` должен быть уникален в объединении «библиотека ∪ его личные колоды». Сервер отказывает в загрузке личной колоды с `id` библиотечной; скрипт администратора предупреждает, если новый `id` библиотеки уже занят чьей-то личной колодой. Проще всего — правило имени: личные колоды начинаются с `my-` (11.4, вопрос 8).

### 4.4. Миграции

- Файлы `migrations/0001_init.sql`, `0002_…` — `wrangler d1 migrations create`, применение — `wrangler d1 migrations apply <база> --remote`; Wrangler ведёт таблицу применённых миграций в самой базе [П — п. 1.3].
- Правило [Р]: только «расширение» (новые таблицы, столбцы с значением по умолчанию, индексы). Удаление и переименование — отдельной миграцией не раньше, чем все устройства обновятся: на телефоне может быть открыта старая версия приложения.
- Когда применяются — п. 1.9 (токен сборки).

## 5. Протокол синхронизации

### 5.1. Обмен пачками

- **Отправка** `POST /api/sync/push` — до 200 записей и до 1 МБ тела [Р]. Ответ — по каждой записи: `stored` (принята), `duplicate` (уже есть, та же), `conflict` (тот же UUID, другое содержимое — ошибка, запись на сервере не меняется), `rejected` + причина (`schema`, `size`, `future`, `user`). Плюс время сервера.
- **Получение** `GET /api/sync/pull?after=<seq>&limit=500` — записи с `seq` больше курсора, по возрастанию, и признак «есть ещё». Клиент хранит курсор в `meta` (только устройство).
- Свои записи тоже приходят при получении (сервер не фильтрует по устройству) — клиент пропускает уже имеющиеся UUID, как при восстановлении (`planRestore`) [Ф — так работает `restoreJournal`].
- Порядок за один сеанс: отправить всё из очереди → получить всё после курсора → пересчитать затронутые карточки [Р].

### 5.2. Идемпотентность и неизменяемость

- Повтор той же пачки безопасен: записи с известным UUID и тем же содержимым — `duplicate` [Р].
- Сравнение содержимого — по SHA-256 **канонического** JSON (ключи по алфавиту, без пробелов), который считает сервер. Тогда повтор с другим порядком полей — не конфликт [Р].
- Тот же UUID и другое содержимое — `conflict`, запись на сервере не меняется (решение Pooya). На клиенте такая запись остаётся в очереди с пометкой «не принята» (5.4). Ожидаемых причин нет — это ошибка в коде, тест должен её ловить.

### 5.3. Проверка на сервере

- Тело — JSON-объект; общие поля обязательны и типизированы, как в `reviveRecord` (`src/core/backup.ts`): `id`, `type`, `userId`, `deviceId`, `at`, `deckId`, `entryId`, `deckRevision`, `sessionId` [Ф — эти поля проверяет восстановление]. Для известных типов (`intro`, `review`, `drill`) — те же проверки, что в `reviveRecord` (код общий: модуль `src/core` подключается и в Worker) [Р].
- `userId` записи = `id` аккаунта сессии, иначе `rejected: user` [Р].
- Запись ≤ 16 КБ (сейчас ≈ 1 КБ) [Р].
- **Время впереди сервера.** Предлагаю **N = 2 часа** [Р]: проверки со сдвигом даты сдвигают её на целые сутки (21→22.10, `docs/STATUS.md`) [Ф] — их ловит любое N < 24; 2 часа покрывают ошибку часов из-за неверного пояса или перевода часов (±1 ч). Отклонённая `future` запись не удаляется: остаётся на устройстве с пометкой и выгружается в файл журнала. Повторно сама не отправляется (иначе через сутки «завтрашняя» запись пройдёт).
- Нижняя граница — `at` не раньше 2026-10-01 (журнал начинается 14.10.2026) [Р].
- Неизвестный `type` — принимается, если общие поля верны (5.5).

### 5.4. Очередь отправки, повторы, частичный сбой

- Новая таблица Dexie `outbox` (UUID записей, ещё не принятых сервером; статус `pending` / `rejected` + причина). Запись в журнал и в очередь — одной транзакцией, как сейчас журнал и карточка в `recordReview` [Р; новая таблица = новая версия схемы Dexie 2, только добавление — данные не переносятся].
- Отправка — через 5–10 с после ответа (пачкой), при запуске, при событии `online` и при уходе приложения в фон (`fetch` с `keepalive`) [Р].
- Ошибка сети или 5xx — повтор с растущей паузой (5 с, 30 с, 2 мин, 10 мин). 401 — сессии нет (выход или аккаунт удалён) — очередь не трогается, экран входа (6). 426 — версия приложения ниже минимальной (5.5).
- Частичный сбой: каждая запись получает свой итог; `stored` и `duplicate` уходят из очереди, `rejected` и `conflict` остаются с причиной. В Настройках: «Не приняты сервером: N» и кнопка «Захираи таърихча дар файл» (файл, как сейчас, — все записи, включая непринятые) [Р].
- Пачка — одна транзакция D1: при сбое посередине не сохраняется ничего, повтор безопасен (5.2) [Р].

### 5.5. Разные версии приложения на устройствах

- **Неизвестные поля и типы.** Dexie хранит записи с любыми полями без объявления [Ф — `docs/DATA_MODEL.md`, этапы 4.2–4.4а добавляли поля без миграции]. Клиент при получении сохраняет запись целиком и при отправке шлёт её целиком — старая версия не теряет полей новой. Пересчёт берёт только `review` [Ф — `rebuildCards`], поэтому будущий тип (например, «практика без оценки» 4.4б) старую версию не ломает.
- **Записи с правилами новее своих.** Если пришла запись `review` с `rules` больше своего `RULES_VERSION` (сейчас 2) [Ф], клиент **не пересчитывает** карточки, а показывает «Барӯзрасонӣ лозим» и перезагружает страницу [Р]. Без service worker перезагрузка даёт свежую версию (`/` — `no-cache`) [Ф — `public/_headers`]; на этапе 7 — через обновление service worker. Записи при этом уже сохранены — после обновления пересчёт верный.
- **Минимальная версия клиента — нужна** [Р]: каждый запрос несёт заголовок `X-Mana-Version` (номер сборки); сервер с константой `MIN_CLIENT` отвечает 426 на отправку от старой версии. Это защищает от записей, сделанных по старым правилам после их смены (например, вкладка, открытая неделю). Поднимать `MIN_CLIENT` — при каждой смене `RULES_VERSION` или формата записи.
- Версия правил по-прежнему в каждой записи (`rules`), пересчёт применяет правила версии записи (Р29.4) [Ф].

### 5.6. Пересчёт FSRS после объединения и тест детерминизма

- Пересчёт идёт на клиенте: `rebuildCards` проигрывает ответы по `at`, затем `id` [Ф — `compareLog`]; пояс — из записи [Ф — Р29.3]; поэтому порядок прихода записей и пояс пересчитывающего устройства на результат не влияют [Р — следует из кода; проверяется тестом ниже].
- Пересчитываются только затронутые карточки (пары, у которых пришли новые ответы) — их история целиком [Р; при 100 тыс. записей полный пересчёт на телефоне может занять заметное время — не замерялось].
- **Снимок `fsrs` в записи** после объединения может не совпадать с пересчётом (на втором устройстве ответ сделан при другом состоянии карточки) [Р]. Это ожидаемо: снимок — только для анализа (`docs/DATA_MODEL.md`) [Ф]. Тест «пересчёт даёт записанный срок» остаётся для журнала одного устройства.
- **Тест (Vitest, без браузера):** две базы fake-indexeddb, общий сервер-заглушка с тем же кодом проверки и курсора; устройство А — Europe/Luxembourg, Б — Asia/Dushanbe; ответы на одни и те же карточки вперемешку, в том числе офлайн и с «Снова» + возвратом (`requeue`); обмены в разном порядке и с повтором пачек. Проверка: на обоих устройствах карточки (`due`, `stability`, `difficulty`, `state`) равны `rebuildCards` по объединённому журналу; повторная синхронизация ничего не меняет [Р].

### 5.7. Лимит новых и граница суток на объединённом журнале

- Лимит считается по журналу за сегодня (Р17.5) [Ф — `introsToday`]; после объединения — по общему журналу, сутки — по поясу этого устройства (Р29.3) [Ф].
- **Два устройства офлайн в один день:** каждое выдаст до лимита, после объединения знакомств за сутки будет до 2 × лимит; следующие порции новых не дадут [Р]. Принять как есть (как «лишний лимит в день перелёта», Р29.3)?
- **Одна запись знакомится дважды** (на обоих устройствах офлайн): `introsToday` считает записи журнала, а не пары колода × запись [Ф — код], значит одно знакомство посчитается дважды. Предлагаю считать уникальные пары [Р, небольшая правка с тестом].
- Долги и «завтра / за 7 дней» — из пересчитанных карточек, поэтому сразу верны [Р].

### 5.8. Записи для колод и записей, которых нет на устройстве

- Записи сохраняются, карточки по ним пересчитываются [Р], но не выдаются и в долги не попадают: `dueCards` берёт только карточки, у которых есть запись колоды [Ф — `src/core/session.ts`]. Установили колоду позже — прогресс появился.
- Знакомства в колодах, которых здесь нет, считаются в лимит новых — лимит общий на пользователя (Р29.5) [Ф — `introsToday` не смотрит на колоды].

### 5.9. Перенос локальных ответов при первом входе

Исходное: у каждой установки свой `userId` и `deviceId` в `meta`; на телефоне Pooya `userId` взят из файла при переезде, `deviceId` новый [Ф — `docs/STATUS.md`, шаг 6.0].

Предложение [Р]:

1. **Аккаунт получает `userId` первой установки, которая переносит ответы.** При погашении приглашения клиент сообщает свой `userId` и есть ли у него ответы. Пользователь выбирает «Пешрафти ин дастгоҳ ба ҳисобатон илова шавад?» (утверждено 21.10.2026) → сервер создаёт аккаунт с `id` = этот `userId` (если он ещё не занят). Записи на телефоне **не переписываются**: `userId` в них уже равен `id` аккаунта. Все записи ставятся в очередь отправки.
2. **Следующее устройство без ответов** (ноутбук с пустой базой) принимает `id` аккаунта в `meta.userId`, как сейчас восстановление принимает пользователя из файла [Ф — `restoreJournal`, `adoptUserId`], и получает журнал.
3. **Следующее устройство со своими ответами** (другой `userId`): перед первой отправкой одна транзакция на устройстве меняет `userId` в своих записях, настройках и карточках на `id` аккаунта; UUID, время, ответы, `deviceId` — без изменений. Прежний `userId` пишется в `user_aliases` на сервере и в `meta` [Р]. На сервере ни одна запись не меняется — переписывание происходит до отправки.
4. **Идемпотентность.** Прервался перенос — повтор: записи с теми же UUID дают `duplicate`. Переписывание `userId` идемпотентно (второй раз нечего менять).
5. **Отказ от переноса** — ответы остаются на устройстве под прежним `userId`, в аккаунт не попадают; файл журнала можно сохранить [Р].
6. **Критерий приёмки** (решение Pooya): даты следующих повторений до и после совпадают. Проверка: перед переносом приложение запоминает (`deckId`, `entryId`, `skill`, `due`) всех карточек; после переноса и получения — сравнивает; на ноутбуке после получения — то же сравнение с телефоном. Тест — на копии настоящего журнала (с разрешения Pooya, в `reference/`, не в репозиторий) [Р].
7. **Снятие отказа при восстановлении из файла.** Сейчас файл другого `userId` при своих ответах — отказ [Ф — `planRestore`]. Со входом: файл `userId` аккаунта или его прежнего `userId` (`user_aliases`) принимается всегда; записи прежнего `userId` переписываются на `id` аккаунта, уже имеющиеся UUID пропускаются, новые уходят в очередь. Файл с неизвестным `userId` — экран «Ин таърихчаи насби дигар аст. Ба ҳисоб илова шавад?» с подтверждением; после него `userId` файла становится прежним `userId` аккаунта [Р; 11.4, вопрос 6]. Без входа поведение не меняется.

### 5.11. Второй аккаунт на одном устройстве (позже) — без миграции

Сейчас: `meta` — одна строка `device`; `log`, `cards`, `settings` уже с `userId` в ключе, но `decks`, `entries`, `media` — общие для устройства, ключ `decks` — только `id` [Ф — `src/platform/db.ts`]. Две личные колоды двух людей с одним `id` на одном устройстве столкнутся [Р].

Предложение [Р]: **у каждого аккаунта на устройстве — своя база IndexedDB.**

- Первый (и сейчас единственный) профиль — база `mana`, как есть; второй — `mana-2`, третий — `mana-3`. Внутри — та же схема Dexie, ничего не переносится.
- Список профилей — маленькая отдельная база `mana-profiles` (номер, имя на экране, вошёл ли); нет её — значит, один профиль `mana`. Экран выбора «Кӣ дарс мехонад?» появляется, только когда профилей больше одного.
- Сессии: cookie одна на адрес сайта, поэтому у профиля N — своя cookie `__Host-mana_s<N>` (у первого — `__Host-mana_s`), а клиент в каждом запросе шлёт `X-Mana-Profile: N`; сервер берёт cookie этого профиля. **Чтобы потом не мигрировать, это закладывается в 6а сразу:** заголовок со значением по умолчанию и имя cookie первого профиля.
- `deviceId` — свой у каждого профиля (своя `meta`); на сервере это просто разные устройства разных аккаунтов.
- Минус: колода, которую учат оба, хранится дважды (звук до 20 МБ) — для семьи допустимо.
- Локальный режим без входа — тоже профиль (база без аккаунта).

## 6. Удаление аккаунта

По просьбе пользователя, скриптом администратора (решение Pooya).

1. **Перед удалением — выгрузка** [Р]: пользователь сохраняет журнал в файл в приложении («Захираи таърихча дар файл» — есть) [Ф]; или скрипт `export` пишет файл из D1 (журнал в формате `mana-journal`, настройки, согласия, список устройств) — для права на доступ и переносимость (раздел 8). Файл передаётся пользователю лично.
2. **На сервере удаляются** строки во всех таблицах с этим `user_id`: `journal`, `user_settings`, `sessions`, `devices`, `pairing_codes`, `invites`, `user_aliases`, `consents` (11.4, вопрос 7), `library_choices`, `quotas`, `decks` и `deck_revisions` личных колод; объекты R2 по префиксу `users/<user_id>/`; затем `users`. Одна пачка D1 + удаление в R2 [Р].
3. **Остаётся:**
   - строка `admin_actions` «аккаунт удалён» с UUID и датой, без имени [Р];
   - **Time Travel D1: 7 дней на Free, 30 дней на Paid** — в течение этого срока базу целиком можно вернуть на момент до удаления [П: 1.3]. Выборочно стереть данные из этой истории нельзя [Р — инструмента для этого в документации нет]. В уведомлении: «полностью удаляются в течение 30 дней»;
   - R2: удалённый объект восстановить средствами R2 нельзя, если нет своей копии [Р — версионирование R2 не проверялось];
   - сетевые данные Cloudflare (IP) для защиты от атак — срок Cloudflare не называет (8.3).
4. **Устройства:** следующий запрос → 401 `account_deleted` → экран «Ҳисоб пок шуд» с двумя кнопками: «Пок кардани додаҳо аз ин дастгоҳ» (стирает базу `mana`) и «Бе ҳисоб идома» (остаётся локальный режим) [Р]. Пока устройство не выходило в сеть, данные на нём остаются — удалить их может только сам пользователь (или очистка данных сайта в браузере).

## 7. Безопасность

### 7.1. Секреты

- **На сервере секретов почти нет** [Р]: токены случайные и хранятся хэшами, подписи (JWT) нет. Единственный кандидат — «перец» для хэша IP в счётчиках попыток (7.3): `wrangler secret put IP_PEPPER`, значение генерирует скрипт и передаёт через стандартный ввод, не печатая.
- **Токены Cloudflare** (сборки — в панели Cloudflare; администратора — в `tools/.env`, в `.gitignore`) [Р]: скрипты читают их сами, передают `wrangler` переменной окружения и никогда не выводят — ни в терминал, ни в логи, ни в отчёты. В отчётах — только «токен есть / нет».
- В клиентском коде ключей нет (правило CLAUDE.md) [Ф].

### 7.2. Ограничение частоты запросов

- **Привязка Workers Rate Limiting** (`ratelimits` в `wrangler.jsonc`): период 10 или 60 с, Wrangler ≥ 4.36.0, общедоступна с сентября 2025; счётчик — **в пределах одного дата-центра**, «permissive, eventually consistent»; ключом советуют брать идентификатор пользователя, а не IP [П: [rate limit binding](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/), [changelog](https://developers.cloudflare.com/changelog/post/2025-09-19-ratelimit-workers-ga/)]. **Доступна ли на Free и сколько стоит — документация не говорит** [П].
- Правила WAF на Free — одно правило на зону; `workers.dev` — не наша зона, вероятно, не применимо [П: [WAF rate limiting](https://developers.cloudflare.com/waf/rate-limiting-rules/); Р].
- Предложение [Р]: (а) **точные счётчики в D1** (`auth_attempts`) — только для входа: погашение приглашения и ввод кода; (б) привязка Rate Limiting (если доступна) — для всего `/api/*` по ключу «сессия или хэш IP»: например, 60 запросов в 60 с; (в) лимит CPU на вызов (Paid) — от «счёта за чужие запросы» (1.8).

### 7.3. Перебор приглашений и кодов

- **Приглашение:** 256 бит — перебор невозможен; счётчик нужен только против нагрузки [Р]. ASVS: при ≥ 112 битах достаточно обычного хэша [П: ASVS V6, 3.2].
- **Код привязки (40 бит):** злоумышленник угадывает любой действующий код, а их одновременно не больше числа пользователей (≈ 20) [Р]. Счётчики: на хэш IP — 10 неудач за 10 мин; **общий** — 50 неудач в час, затем ввод кодов закрыт на час для всех (вход по ссылке администратора работает). Оценка: даже при постоянном переборе на пределе (≈ 440 тыс. попыток в год) вероятность угадать за год ≈ 440 000 × 20 / 2⁴⁰ ≈ 8 · 10⁻⁶ [Р]. NIST допускает до 100 неудач подряд [П: 3.2].
- Ответ на неверный код или приглашение — одинаковый, без подсказки «истёк» / «не существует» [Р].

### 7.4. Размер запросов

- Проверять `Content-Length` и читать тело с подсчётом байт, обрывая на пределе (413) [Р]: отправка журнала — до 1 МБ; погашение и вход — до 4 КБ; загрузка колоды (6б) — до 25 МБ (тело запроса Worker — до 100 МБ, 1.2 [П]).
- Неподдерживаемый `Content-Type` — 415 [П: [OWASP REST](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html)].

### 7.5. Заголовки ответов API

Задаются кодом Worker (`_headers` не применяется, 1.1). По OWASP REST [П]: `Content-Type: application/json; charset=utf-8`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`, `Referrer-Policy: no-referrer`, `Strict-Transport-Security: max-age=31536000`; CORS выключен; ошибки — короткий код без трассировки стека. Плюс `Cross-Origin-Resource-Policy: same-origin` [Р]. CSP страницы (`connect-src 'self'`) уже разрешает `fetch` к `/api/*` [Ф — `public/_headers`].

### 7.6. Загрузка личных колод (6б)

- **CPU:** на Free — 10 мс на запрос [П] — распаковать на сервере архив 20 МБ, скорее всего, не уложится [Р]. Варианты: проверка архива на сервере — на Workers Paid; или на Free — полная проверка в приложении (уже есть) + на сервере только дешёвая проверка оглавления ZIP и `deck.json`.
- **Что проверять на сервере** [Р; основа — OWASP: предел размера — после распаковки, П: [OWASP File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)]:
  - архив ≤ 25 МБ; записей в архиве ≤ 1 000; ZIP64 не нужен — отказ;
  - имена: только `deck.json` и `audio/<имя>.mp3|wav`; отказ при `/` в начале, `\`, `:`, NUL, сегменте `..`, пустом сегменте, повторе имени (в том числе с другим регистром или иной Unicode-нормализацией); записи-папки и символьные ссылки (биты режима Unix во внешних атрибутах) — отказ; зашифрованные записи (флаг 0) — отказ; методы сжатия только 0 и 8 [П: zip slip — [Snyk](https://security.snyk.io/research/zip-slip-vulnerability); Р — список];
  - размеры из оглавления: `deck.json` ≤ 2 МБ, файл звука ≤ 5 МБ, сумма после распаковки ≤ 60 МБ, отношение сжатия у записи ≤ 100 (без перекрытия данных DEFLATE даёт не больше ≈ 1 032 [П: [bamsoftware](https://www.bamsoftware.com/hacks/zipbomb/)]; звук почти не сжимается — Р); оглавление и локальные заголовки совпадают, данные записей не перекрываются;
  - **при распаковке считать байты и обрывать на заявленном размере** — размеры в заголовках могут лгать [П: bamsoftware; Р]; проверить CRC;
  - `deck.json` — тем же валидатором `checkDeckArchive`, что приложение (код `src/core` подключается в Worker) [Р].
- **Библиотека:** fflate 0.8.3 — без зависимостей, ≈ 5 КБ, `unzipSync` с `filter` даёт `size` / `originalSize` из оглавления до распаковки; поддержка Workers официально не заявлена; по исходнику (не проверено) выход обрезается по заявленному размеру и CRC не проверяется [П: [fflate](https://github.com/101arrowz/fflate)]. JSZip (уже в зависимостях) — держит весь архив в памяти, размеров до распаковки не даёт, поддержка Workers не заявлена [П: [JSZip limitations](https://stuk.github.io/jszip/documentation/limitations.html)]. @zip.js/zip.js — без зависимостей, но были ошибки на Workers с обходами [П: [#434](https://github.com/gildas-lormeau/zip.js/issues/434), [#513](https://github.com/gildas-lormeau/zip.js/issues/513)]. Рекомендация [Р]: **свой разбор оглавления (≈ 150 строк) + распаковка только `deck.json` встроенным `DecompressionStream('deflate-raw')` со счётчиком байт** — без новой зависимости; есть ли `deflate-raw` в Workers — проверить до 6б. Запасной вариант — fflate (с объяснением, как новая зависимость).
- **Квоты** (предложение) [Р]: личная колода ≤ 25 МБ (предупреждение с 20 МБ остаётся — Р15 [Ф]); ≤ 20 личных колод; всего ≤ 100 МБ на пользователя; хранить 3 последние редакции колоды. Итог 20 × 100 МБ = 2 ГБ — в бесплатных 10 ГБ R2 (1.8).

## 8. GDPR-минимум

### 8.1. Применяется ли GDPR

- Исключение «purely personal or household activity» (соображение 18) толкуется узко (дело Ryneš, C-212/13) [П: [recital 18](https://gdpr-info.eu/recitals/no-18/); пересказ решения — [inforrm](https://inforrm.org/2014/12/17/bringing-data-protection-home-the-cjeu-rules-on-data-protection-law-and-home-cctv-lorna-woods/); текст решения на CURIA не открылся]. У нас — сервис в интернете, 10–20 человек не одного домохозяйства, чужие дети: **считаем, что GDPR применяется** [Р].
- DPO не нужен (ст. 37(1): органы власти, крупномасштабное наблюдение или особые категории) [П: [Art. 37](https://gdpr-info.eu/art-37-gdpr/); Р]. Исключение из реестра обработки (ст. 30(5)) не действует для обработки, которая «is not occasional» [П: [Art. 30](https://gdpr-info.eu/art-30-gdpr/)] — ежедневный журнал не эпизодичен: **нужен короткий реестр обработки** (одна страница; где хранить — 11.4, вопрос 12) [Р].

### 8.2. Основание и согласие родителя

- Ст. 8 действует, **только если основание обработки — согласие** (EDPB 05/2020, п. 127) [П: [EDPB Guidelines 05/2020](https://www.edpb.europa.eu/our-work-tools/our-documents/guidelines/guidelines-052020-consent-under-regulation-2016679_en)]. При основании «договор» (ст. 6(1)(b)) действуют национальные правила о договорах с несовершеннолетними [П/Р].
- Предложение [Р]: основание — **согласие** (ст. 6(1)(a)); отзыв согласия = удаление аккаунта. Так решение Pooya «до 16 — согласие родителя» прямо ложится на ст. 8.
- **Возраст по странам:** официальной сводной таблицы по 27 странам **не найдено**; EDPB: оператор должен учитывать возраст в каждой стране, где оказывает услугу (п. 131) [П]. Вторичная таблица (18.04.2026): DE 16, FR 15, NL 16, AT 14, IE 16, ES 14, IT 14, SE 13, BE 13, PL 16, LU 16 [П: [sota.io](https://sota.io/blog/gdpr-art-8-childrens-consent-age-verification-parental-authorization-digital-services-developer-guide-2026)]; по CZ источники **расходятся** (13 или 15) [П]. **16 — наибольший возраст в ЕС**, поэтому одно правило «до 16» подходит для любой страны [Р]. **Люксембург (Pooya живёт там, надзорный орган — CNPD): 16 лет.** Закон от 01.08.2018 (Mémorial A № 686 от 16.08.2018, организация CNPD и применение GDPR) не содержит положения о возрасте согласия ребёнка — слово «enfant» в тексте не встречается ни разу, есть только главы о CNPD, свободе выражения, исследованиях, особых категориях, тайне [П: [Legilux, PDF](https://data.legilux.public.lu/file/eli-etat-leg-loi-2018-08-01-a686-jo-fr-pdf.pdf), прочитан текст опубликованной редакции 21.10.2026]. Значит, Люксембург возраст не снижал, и действует общее правило ст. 8(1) GDPR — 16 лет [Р; совпадает со вторичным источником [luxgap](https://luxgap.com/lois/rgpd/art-8/)]. Последующие изменения закона (сводная редакция) не проверялись.
- **«Разумные усилия» проверить родителя** — соразмерно риску: при низком риске хватает самооценки «есть 16 / нет»; если человек говорит «нет 16» — верить без проверок и получить согласие родителя; собирать минимум; пример EDPB — согласие по почте родителя (пп. 134–142) [П, EDPB]. У нас почты нет. Предложение [Р]: (1) администратор отмечает «до 16» в приглашении — он лично знает семью; (2) экран при входе «Мне есть 16 / нет»; (3) если «нет» или отметка — экран для родителя на том же устройстве: имя родителя, отметка «Я родитель или опекун и согласен», версия уведомления → строка `consents` (`given_by: parent`, имя, время, версия). Ст. 7(1) требует, чтобы оператор мог доказать согласие [П: EDPB; [Art. 7](https://gdpr-info.eu/art-7-gdpr/)] — эта строка и есть доказательство.
